# Research Limitations

These limitations are documented honestly and must appear in the paper. They represent genuine constraints on the scope and generalisability of this research.

---

## L1 — Synthetic Telemetry
All telemetry data was generated by parameterised scenario profiles (normal_stable, memory_gradual_leak, cpu_sudden_failure, disk_gradual_exhaustion, network_degradation, combined_gradual_failure). These profiles simulate realistic failure patterns but do not capture the full complexity, noise characteristics, or interdependencies of real production cloud infrastructure. Results cannot be assumed to generalise directly to real environments without further validation.

## L2 — Simulated Recovery Actions
Healing actions are rule-based strings selected by the decision engine (e.g., "Restart affected service / reclaim memory"). They are not executed through real cloud orchestration APIs such as AWS Systems Manager, Kubernetes HPA, or GCP Cloud Functions. The system does not perform actual resource reallocation, container restart, or network route changes. All recovery remains within the simulation layer.

## L3 — Sudden Failure Detection Difficulty
The cpu_sudden_failure scenario achieves the lowest predictive F1 (0.529 at seed 42) among failure scenarios. This is expected: abrupt step-change failures produce limited temporal trajectory signals before onset. Gradual failure scenarios (memory leak, disk exhaustion) are better suited to temporal feature-based prediction.

## L4 — Root-Cause Inference is Not Causal Proof
The likely-failure-category classifier maps XAI attribution strengths across resource dimensions (CPU, Memory, Disk, Network) to infer which subsystem is most likely responsible. This is based on observed telemetry patterns and model evidence, not on access to system call traces, kernel logs, or controlled causal experiments. The classification is a probabilistic inference, not a mechanistic causal diagnosis.

## L5 — Post-Healing Verification Uses Simulated Normal Telemetry
The post-recovery re-evaluation generates a synthetic 10-step normal baseline sequence and evaluates it with the same model. This confirms that the model treats stable synthetic telemetry as low-risk, but it does not confirm that the real infrastructure state has recovered. The verification is a model-level consistency check, not a real system health assessment.

## L6 — Model Training During Initialisation
The integrated system trains the Logistic Regression model from the Phase 3C seed-42 training dataset at server startup. This is a prototype-appropriate approach for a research demonstration, but not suitable for production deployment where model governance, versioning, and update pipelines would be required.

## L7 — Single Integrated Model
The integrated system uses only Logistic Regression. While Gradient Boosting achieved marginally higher mean AUC in comparative evaluation, deploying it would require an approximation-based XAI method (e.g., SHAP) rather than the deterministic coefficient attribution used here. This trade-off is documented as a conscious design decision, not an oversight.

## L8 — Labelling Methodology
The prediction target label is defined as: failure active in the current timestep OR within the subsequent 10 timesteps. This means MEDIUM and HIGH risk predictions early in a failure trajectory are labelled positive even before resource metrics reach critical values. The label construction is appropriate for early-warning but means predictions are not purely future-looking.

## L9 — No Real-World Validation
The system has not been tested on real cloud infrastructure. Validation with real infrastructure data (e.g., from Google Cluster workload traces, Microsoft Azure traces, or Alibaba cluster traces) is identified as future work.
